# Processing architecture and performance diagnostics (v71)

## Three stages

1. **Games — Game Retrieval (Lichess)**: stream PGNs once on list creation and count/index games. Automatic hand-off to Positions. I/O is mostly remote-network transfer; no chess engine required. Download is chunked (1 MiB), with a small SQLite status update for each chunk. The Process card displays `Lichess transfer` and `PGN indexing` when measured. Old completed lists show their known wall duration, if available.
2. **Positions — Position Evaluation (Stockfish)**: parse each game's PGN; run shallow engine searches over candidate moves, then deep-confirm selected mistakes/brilliancies, optionally test explanatory replies, and collect proactive coaching evidence on **retained** positions. This is typically the dominant cost of initial setup, because every candidate invokes one or more engine searches. The analysis-job checkpoint caches already analyzed games at a matching analysis version and settings signature. The Process card breaks down measured cumulative time into `Screening`, `Deep evaluation`, `Reply checks`, `Coaching probes`, `Metadata`, and cached-game count. These are per-job totals, potentially across multiple passes and pauses, not per-position predictions.
3. **Coaching — Coaching Analysis (Stockfish + built-in coach)**: reprocess saved training positions, independently inspect specific opponent replies with Stockfish, then regenerate taxonomy, difficulty, opening and explanations from saved authoritative deep evaluations. This does **not** retrieve games, rescreen games or overwrite their root Stockfish evaluations. The default 1.2 seconds *per position* for bounded proactive probes (two candidate root moves, default MultiPV=2) makes a fresh 500-position refresh cost roughly **10 minutes of engine-search budget**, plus engine startup and metadata computation. Actual time may differ considerably depending on hardware, position, depth cap, search overhead and SQLite.

## Optimizations implemented in v71

- **Exact-input coaching probe reuse**. Versioned JSON saved with each position now has a SHA-256 `cache_key` of its board, candidate moves, root evaluations, alternative lines, probe version, Stockfish engine name and relevant search settings. Re-running Coaching with unchanged inputs reuses that evidence instead of repeating its MultiPV engine searches. Metadata and explanations are **still rebuilt**, so new coaching code can reinterpret the saved evidence. Legacy v70 probes have no key and are intentionally searched once. A changed search depth, time budget, variation count, Stockfish version or saved root analysis invalidates reuse. Changing a model's *interpretation* code does not need to invalidate a sound engine search. Future changes to the **probe generation code** must bump `PROACTIVE_VERSION` to invalidate the cache.
- **PGN reuse across batches**. Coaching batches keep a bounded 64-game least-recently-used classification/game-history cache. The opening classifier accepts the game already parsed for move history, eliminating a second chess.pgn parse per game. The cache is per worker and never persisted across jobs.
- **Persisted stage timings**. A `perf_json` column is added non-destructively to `retrieval_processes`, `analysis_jobs`, and `metadata_processes`. Timings are collected with `time.perf_counter()` for completed units and checkpointed with their process progress. Process displays these figures on subsequent polls, including after completion. Historic runs have no detailed timings; they are not reconstructed. Metadata timing includes DB/CPU generation and is measured before the batch commit, so a little commit overhead is not represented. Times are cumulative across resumed sessions.
- **No changes to resource-intensive search quality defaults**. The app does not silently decrease Stockfish depth, time, MultiPV, or confirmation criteria to gain speed. Per-job engine reuse, bounded metadata transactions, pauses/resumes and source-PGN retrieval isolation remain intact.

## Profiling protocol for the next local run

1. Upgrade to v71, preserving `data/` and the Stockfish executable.
2. Open **Process**, run **Coaching Analysis** for an existing game list. All v70 probe data will be reprobed once to receive the new input key; later unchanged coaching refreshes should report substantial `reused` counts and much lower `Stockfish probes` time.
3. Compare first-pass and second-pass total `Stockfish probes` and `Metadata` time. If metadata dominates, inspect game PGN sizes and classifying/label recomputation. If Stockfish dominates on a first pass, adjust the Settings coaching time/depth/MultiPV only with an explicit accuracy/latency tradeoff measured against Coach feedback.
4. Newly created game lists report measured Games and Positions phase durations; old lists cannot retroactively report the breakdown. For the first Positions run, deep evaluation generally dominates, while excellent/brilliant candidate selection may increase shallow MultiPV usage.
5. Preserve positive approved feedback when reviewing changes. Probe caching changes search frequency, not evidence or motif-selection rules. Review coaching accuracy against the full feedback benchmark after changing quality settings.

**Boundary:** timings are profile instrumentation, not a rigorous benchmark. `PROCESS_LOCK` enforces sequential engine-intensive jobs, so external wait times, scheduling, engine startup and partial interrupted games may not be included in the counters. A repeat full **Positions** Analyze next-pass will still perform new Stockfish searches where appropriate; only identical completed game caches are skipped.
